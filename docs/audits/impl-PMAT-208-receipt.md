## What failed, on the real release

`forjar dist` resolves checksums from `https://github.com/<repo>/releases/download/<tag>/<asset>`. GitHub does not serve that path while the release is a DRAFT — which it is until `publish-release` un-drafts it, by the design RULE 3 pins. The 1.26.0 run uploaded all thirteen assets and then died:

```
error: cannot resolve checksums for release asset(s) forjar-1.26.0-x86_64-unknown-linux-gnu.tar.gz, ...
```

The installer was generated by hand from the tag so the release could ship, and this ticket is the repair.

## The fix

A step before the dist step fetches the checksums over the authenticated API, which does see a draft, and the dist step is told to use them:

```yaml
- name: Fetch the release checksums (the release is still a DRAFT here)
  run: |
    gh release download "$RELEASE_TAG" --repo "${{ github.repository }}" \
      --pattern SHA256SUMS --dir /tmp
    test -s /tmp/SHA256SUMS
```

with `--checksums-file /tmp/SHA256SUMS` on `forjar dist`. The checksums come from the release itself either way; the only change is that they arrive over the API rather than the public URL.

## The merge review refuted the gate, and it was right

RULE 8 was added to pin the shape: the fetch, the flag, and their order. Three merge-review lanes independently found it vacuous — it searched the whole `dist-artifacts` job text for `--checksums-file`, and the step's own comment names the flag while explaining why it is there.

Measured, not accepted: the argument was deleted from the command with every comment left in place, and the rule reported `8 passed`. The gate written to keep this failure closed was reporting green with the fix removed.

The job text now drops comment lines before any search, and the flag is looked for after the `dist` command rather than anywhere in the job. The same mutation now reports `7 passed; 1 failed`. Deleting the `gh release download` command with its comment left in place used to fail on the wrong assertion, quoting the comment back as the offending text; it now fails on `dist-artifacts never fetches the checksums over the API`. A third lane finding, an unbounded slice that would panic instead of naming the rule on a shorter job, is fixed by clamping every window.

Two lanes of the PRE-MERGE round had called RULE 8 non-vacuous. They were wrong, the merge round caught it, and `.quorum/evidence/dist-draft-refuters.md` records that rather than tidying it away.
