# Independent review — agy /teamwork-preview — PMAT-162

The plan-stage /teamwork-preview grill of PMAT-161 (conv-aea0ebd6, 274 s) is the independent-stack review that established the shared-dir hazards this spec answers — global generations keyed by machine name, whole-map outputs, status attribution — before any spec text existed; the v1 review's three lanes (conv-d1483f00, conv-17a7ff24, conv-d2f80a07) are quoted below as the first adversarial pass over the design.

## Plan grill (do-not-implement-as-written)

The plan treats the GH-377 warning as a mere annoyance instead of a fatal architecture mismatch. Forjar's state directory is fundamentally single-stack: generations are global and interleave destructively (`copy_state_to_generation`), `forjar status` aggregates globally, and `persist_outputs` overwrites entirely. Sharing a state directory across stacks will irreparably break `undo` math and silently wipe cross-stack outputs. Furthermore, using absolute file paths as identity breaks CI and team workflows, and the proposed migration causes silent data loss upon 1.0 downgrade.

(2) Per-stack sequences are critically safer. A single global sequence fatally breaks `apply --rollback-on-failure`. Currently, `maybe_rollback_generation` (src/cli/helpers_state.rs:146) rolls back to the global `pre_apply_generation`. If stack A fails after stack B applied, the global generation is B's. ## v1 review lane 3 (do-not-implement-as-written)

(1) Implementability and falsifiers: R1-R8 are largely implementable, and the falsifiers discriminate correctly. However, R3 is not implementable as written because `cmd_undo` takes a `u32` for `generations` (defaulting to 1), making it impossible to distinguish "no target" (to select newest owned) from `--generations 1`. R7 is not truly additive because older versions of `restore_generation_to_state` will leak `owner.yaml` into the live state on downgrade.
(2) Single global sequence vs per-stack: A single global sequence is currently safer for `apply --rollback-on-failure` (which expects a single global `pre_apply_gen` to revert to) and `--generations N` arithmetic. Per-stack sequences would break `maybe_rollback_generation` and the `undo --resume` ledger format (which stores a `u32` generation ID). However, moving the global `current` symlink backward after a scoped restore (R4) corrupts the timeline for other stacks.
(3) R4's scoped restore atomicity: `restore_generation_to_state` is not atomic (uses iterative `remove_dir_all` and `copy`). Furthermore, switching the `current` symlink backward after a partial restore abandons newer generations for other stacks. The spec must require `undo` to append a NEW generation (a revert commit) instead of rewinding the pointer.
(4) R5/R7 legacy handling: "Restorable only in a single-stack dir" is correct. However, the migration is NOT additive. Older versions of `restore_generation_to_state` only ignore `.generation.yaml` and `APPLIED_CONFIG`. A new `owner.yaml` will be copied into the live state on downgrade. The owner data must be added to `.generation.yaml` (GenerationMeta) instead.
(5) R6 destroy scoping: It is well-defined. `absent_from_target` flattens resource IDs into a `Vec<String>`, dropping the machine context. However, resource IDs are unique within a `ForjarConfig`'s `resources` map, so `narrowed_config` safely and accurately retains the correct resources for the invoking stack.

Rewinding a global pointer truncates other stacks' history.

## What became of it

Every finding of those four lanes is folded into the spec (D1, D2 in the claims dossier); the design that survived nine rounds keeps their three structural rules — ownership carried in the generation's own metadata, restore scoped to the invoking stack's declared machines with the destroy step after the decision, and one decision function every writer calls.
