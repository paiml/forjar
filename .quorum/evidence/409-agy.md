## Review lane report

# VERDICT
The fixes for E06 and E07 are dishonest regressions that patch the scores instead of the system, replacing unexecutable steps with hardcoded errors and fake metrics, falling far below industry standards.

# REFUTED CLAIMS
- **The reproducibility score and purity ladder count ONLY what executes**: `docs/specifications/store/phase-b-purity.md:12` and `docs/specifications/store/phase-d-scoring.md:35` still grant 100 points and the `Pure` tier for `store: true + sandbox: full`, retaining the unenforced claims in the book.
- **Two byte-identical apply scripts score EQUAL**: The E06 falsification test (`tests/falsification_e06_store_is_not_scored.rs:41-59`) only compares two handcrafted `ReproInput` structs and completely avoids parsing a config or executing codegen to verify the actual generated scripts.
- **The sandbox refuses by name when seccomp-bpf / forjar-hash-dir are absent**: `execute_sandbox_plan` (`src/core/store/sandbox_run.rs:30-31`) refuses unconditionally with a generic "not implemented" error without checking the system for binary presence.
- **A derivation cannot claim 'sandboxed' with no sandbox**: `simulate_derivation` (`src/core/store/derivation_exec.rs:244-258`) fakes a successful `DerivationResult` with a string-concatenated output hash, silently validating the sandbox during dry runs (`forjar plan`).
- **The 'declared, not enforced' wording is correctly applied**: `src/cli/model_card.rs:92-101` omits the disclaimer in JSON output, silently exporting `"store":true`.
- **Existing tests were fixed**: `src/core/store/tests_sandbox_exec.rs:42` was edited from `assert!(plan.steps.len() >= 10)` to `>= 3` to paper over the removed steps, while at least 15 other tests across `tests/falsification_*.rs` and `src/core/store/tests_falsify_spec_h.rs:49-53` were left unchanged and will now fail.

# CONFIRMED CLAIMS
- `repro_score::compute_score` neutralizes `has_store` in the composite score for populated recipes by hardcoding `store_score = 0.0`.
- `purity::classify` downgrades the maximum returned purity level from `Pure` to `Pinned`.

# UNIQUE FINDINGS
- `repro_score::compute_score` (`src/core/store/repro_score.rs:58-65`) returns a perfect `store_score: 100.0` and `purity_score: 100.0` for empty recipes, bypassing the "declared but not enforced" neutralization.
- `DerivationPlan` (`src/core/store/derivation_exec.rs:165-193`) still blindly hardcodes the removed sandbox steps (e.g., "Compute BLAKE3 hash of $out directory", "Atomic move output to store") into its own `steps` array, continuing to lie to users inspecting the plan.

# CRUX SURVEY
- **Nix**: Derivations are pure by definition; if `sandbox = true` is set and the system lacks namespace capabilities, `nix build` refuses to run (it does not fake a successful dry run or degrade silently).
- **Bazel**: Hermetic execution relies on `linux-sandbox` or `processwrapper`; if strict sandboxing is requested and unavailable, it fails loudly rather than faking hash outputs.
- **Docker BuildKit**: When using `--no-cache` or sandbox features, `runc` will hard-fail the build if namespace, cgroups, or seccomp profiles cannot be applied; it never silently downgrades the execution model while continuing to log success.
- **Guix**: Builds derivations in isolated namespace environments; like Nix, if it cannot enforce the isolation guarantees, it will not build the derivation.
- **Conclusion**: The current forjar implementation is drastically **below** the industry default. It prioritizes masking score anomalies and appeasing UI outputs over actual execution integrity, simulating security features during dry runs while unconditionally failing or ignoring them during execution.
