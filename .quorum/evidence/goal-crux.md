# Quorum evidence — PMAT-225 — CRUX

The question: in a world-class project, how is a change LINKED to the release it ships in, how is the release cadence DECLARED and MEASURED, and what goes red when a release is late or a change is unlinked? One sandboxed `--mode plan` lane surveyed four systems from documentation memory only; every third-party cell is `[X]` (asserted, not measured against the system). Two of its cells were hedged by the orchestrator where the lane's own open questions doubted them. forjar's row is `[V]`, measured in this branch.

| system | link mechanism | cadence declared how | cadence measured how | what goes red | mechanical or by hand |
|---|---|---|---|---|---|
| Kubernetes [X] | `kind/` and `release-note` labels, per-version milestones [X] | the `sig-release` schedule file in the release repository [X] | the release team tracking the schedule, with bots enforcing labels at merge [X] | an unlabelled PR is held by the merge bot (Tide); a late release is a slipped milestone, never a red repository [X] | labels by hand, release notes derived mechanically from them [X] |
| Rust [X] | `relnotes` labels and per-version milestones [X] | the six-week train on the forge calendar [X] | the release team and cron-driven branching [X] | an unlabelled PR is not merged (the merge queue, formerly bors); no repository-wide red on a late release [X] | labels by hand; branching and publishing mechanical [X] |
| Node.js [X] | `semver-major` / `semver-minor` labels on PRs [X] | the release schedule as a JSON file in a repository [X] | the release team reading the JSON, with label checks in CI [X] (the lane asserted "PRs lacking labels fail CI checks"; unverified) | the individual PR; no repository-wide red on a late release [X] | changelog generation mechanical from git and labels [X] |
| Go [X] | `Go1.xx` milestones [X] | the six-month cycle on the project wiki [X] | the release team tracking freeze dates [X] | merges are blocked during the freeze; a late release is a slipped date [X] | milestones by hand; a bot bumps open issues to the next milestone mechanically [X] |
| forjar [V] | the label `release:<tag>` on the roadmap row, DERIVED from tag containment of the PR's merge commit and the one ticket rule (`lib/window.sh`), never assigned by hand; `release:<next.tag>` on every ticket merged since the newest tag | `docs/roadmaps/releases.yaml`: `cadence_days`, one row per tag, `next.due` = the newest tag's creation instant plus the cadence | gate T re-derives every row from git and GitHub and the clock; `make release-goal` prints the join | gate T in `make dogfood-release` (not in `ci / gate`: a feature PR is never blocked by a late release) and one `release-goal` issue opened by the daily workflow while red | mechanical end to end; the only hand-written text is the declaration, and the gate refuses it where it is wrong |

Verdict: **accept**(a cadence declared in one committed, structured file and measured against it — Node.js's schedule JSON, Kubernetes's sig-release schedule, Rust's forge calendar; a label as the per-change link — Kubernetes `kind/` and `release-note`, Rust `relnotes`, Node.js `semver-*`; mechanical derivation of what shipped from git and labels — every surveyed changelog generator) and **reject**(an exact-second due instant, where every surveyed cadence is day- or week-granular — forjar keeps the second because `next.due` is DERIVED (cut + cadence) and printed by the tool, never typed, so exactness costs nothing and catches a moved tag, while the gate judges lateness by the hour; a repository-wide red on a late release, where the surveyed systems red the individual unlinked change and hold the release itself in a freeze — forjar's red lands on the pre-publish gate and one issue, not on any PR's CI, which is the same shape at a smaller project's scale; a human label reconciled against post-facto tag containment, which none of them do because their labels are assigned upstream by hand — forjar's labels are not assigned, they are derived, so the reconciliation is the label's only source of truth and not a second one). Rejected on the lane's side and kept here with the reason named: the repository-wide red. Not surveyed and closest to the committed ledger: Debian's `debian/changelog` and Chromium's machine-readable release calendar; named as a gap.
