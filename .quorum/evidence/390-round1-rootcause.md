## Lane summaries

### output-path
The leading hypothesis is not merely possible — it is confirmed, and I reproduced the reporter's exact symptom on localhost in 30 seconds. On the `forjar apply` path a task's STDOUT is captured by the transport, hashed for state-query purposes, written to an on-disk run log, and NEVER printed to the console at any verbosity, flag, output mode or env var. The single operator-visible failure line is `eprintln!("JIDOKA: {}/{} failed — dependents will be skipped: {}")` at src/core/executor/resource_ops.rs:144-147, whose payload is built at resource_ops.rs:411 as `format!("exit code {}: {}", out.exit_code, out.stderr.trim())` — stdout is structurally absent from the string. Running a task that echoes to stdout and emits `CMake Warning` lines to stderr, with a failing `completion_check`, produced console output in which the stdout echoes are missing and the stderr CMake lines are present verbatim — the reporter's symptom exactly. The transport applies no truncation of any kind (ssh.rs:168-172, local.rs:31-35 use `wait_with_output` + `from_utf8_lossy`, uncapped), so nothing was cut off; it was never routed to the console. Escalation is unavailable: `-v`, `-vv`, `-vvv` and `--trace` are byte-identical because `src/cli/dispatch.rs:41` collapses the clap count to `verbose > 0`, and the `VerbosityLevel` enum whose `-vvv` doc says "Stream raw stdout/stderr to terminal in real-time" has ZERO non-test consumers. `--json` and `--output events` are worse than useless: both report `"error": null, "exit_code": null` for a FAILED resource. The stdout does survive to `state/<machine>/runs/<run_id>/<res>.<action>.log`, but only `forjar logs --resource <id>` prints that body, the failure message never names it, `--state-dir` defaults to the relative path `"state"` (apply_args.rs:61) so a stateless CI runner deletes it with the checkout, and the parallel-wave path never writes it at all.

### replay-cache
Transcript replay is structurally impossible in forjar 1.23.1 and the reporter's theory is refuted on both code and experiment. `ExecOutput` (src/transport/mod.rs:126-134) derives only `Debug, Clone` — it has no serde impl, so it cannot be written to or read from disk in any form; all four non-test construction sites (local.rs:31, ssh.rs:168, container.rs:43, pepita.rs:71) build it inline from a just-reaped `child.wait_with_output()`. Nothing on the apply path reads a run log, an event log, or the store cache back into an execution decision: `capture_output` writes .log/.json/.script and the only readers are `forjar logs`; `store::` appears zero times under src/core/executor, src/core/planner and src/resources. The single mechanism in the whole codebase that skips executing a planned change is FJ-2701 task-input caching (resource_ops.rs:249-256), which is opt-in (`#[serde(default)] pub cache: bool` = false), lives only on the sequential path, and returns `ResourceOutcome::Unchanged` — every skip producer in the executor yields Unchanged or Skipped and NONE can yield `Failed`, so the reporter's "1 failed / exit code 1 / task=not-converged" outcome is reachable only through the `Ok(out)` non-success arm that requires a real process result. I reproduced the reporter's symptom byte-for-byte locally and instrumented it: across 6 applies (3 plain, --refresh, --force, --force-unlock) an append-only counter went 1→6, proving the command re-ran every single time while the operator-visible message stayed identical. Editing the command mid-experiment made the new STDERR line appear instantly and the new STDOUT line never appear at all — the leading hypothesis, confirmed. The one genuinely new finding in this lane is why the reporter could not find the output "anywhere in the full raw apply log": under parallel wave execution forjar writes NO run log at all — an A/B control with the same config and only `policy.parallel_resources` flipped produced 8 log files sequentially and a non-existent `state/box/runs/` directory in parallel.

### script-gen
forjar cannot be executing a stale script. The apply path regenerates the shell from the freshly-parsed, freshly-resolved resource on every single run (`resource_ops.rs:272`, `machine_wave.rs:27`); `PlannedChange` carries no script text; the bashrs/I8 gate lints a throwaway `strip_data_payloads` copy and can only REJECT, never rewrite (`transport/mod.rs:158-167`); the only mutation applied to the executed bytes is a one-line `{ … } < /dev/null` wrapper; and the only reader of the persisted `.script` sidecar is `forjar logs --script`. I emitted the reporter's resource shape through the shipped 1.23.1 binary and every line of the command is present, verbatim, in order. I then REPRODUCED the reporter's exact console output — same `JIDOKA … exit code 1: <cmake warning>` + both `task=not-converged` lines — with a task whose command runs perfectly and writes its diagnostics to STDOUT, confirming the observability hypothesis. Two decisive measurements settle it: (a) an early `set -e` abort produces a completely DIFFERENT message (`exit code 127: bash: line N: …: command not found`, no not-converged lines), positively ruling out the rival "the earlier lines aborted" explanation for the reporter's exact output; (b) real cmake writes every `--` progress line to STDOUT and `CMake Warning` to STDERR, and its STDERR is byte-for-byte identical between a fresh configure and a 0.03s incremental one while its STDOUT shrinks — so "identical warnings every run" is evidence of determinism plus stderr-only reporting, not of a replayed transcript. I also found three real, separate script-gen defects that the lane must report: with `timeout:` set the command runs in a nested `bash` that does NOT inherit `set -euo pipefail` (so under `timeout:` the reporter's exit-0 does NOT prove every line succeeded), that same nested heredoc re-opens the FJ-2732 stdin-eating hole, and the parallel/wave path writes no run logs at all — destroying the one place stdout survives.

### transport
I read src/transport/{mod,ssh,local,container,pepita,stdin_isolation}.rs end to end and then reproduced the reporter's exact symptom over a REAL SSH transport (forjar 1.23.1, machine addr 127.0.0.2/127.0.0.3 so `machine_is_local` is false and `ssh::exec_ssh` is taken — verified by the remote reporting `ppid-cmd: sshd: <user>@notty`). The transport layer delivers the script on the child's STDIN (never argv), captures stdout and stderr into two separate pipes, allocates no TTY, streams nothing, and caches nothing. A 228 KB script and 3.4 MB of remote stdout crossed intact with no truncation and no deadlock. Three consecutive applies executed the remote command three times (append-only marker file has three lines) while printing a byte-identical operator message — identical because stderr is deterministic, not because anything was replayed. The leading hypothesis is CONFIRMED and is specific to no transport at all: `exec_ssh` (ssh.rs:164-172) returns a complete `ExecOutput{stdout, stderr}`, `run_capture` writes BOTH to disk, and then `resource_ops.rs:411` / `machine_wave.rs:180` format the operator's only console line from `out.stderr` alone. My repro printed `exit code 1: CMake Warning: … CMAKE_BUILD_TYPE=Release … task=not-converged: …` with the two stdout `echo` diagnostics nowhere on the console, while `state/gx10/runs/<run>/llama-cpp-build.create.log` held them verbatim under `=== STDOUT ===`. Along the way I measured three genuine transport defects unrelated to #390's symptom: `--timeout` is effectively inert over SSH (48 s wall for `--timeout 3`, inode-proven cause), a transport timeout writes NO run log at all, and `sudo: true` re-opens the FJ-2732 script-eats-itself defect that the stdin-isolation wrapper was written to close.

### plan-freshness
The plan-freshness chain is clean end to end and cannot produce the reported symptom: `forjar apply` re-reads the YAML from disk on every invocation, `PlannedChange` carries no command or script, and the executed script is generated at execution time from the freshly parsed `Resource`. There is no plan cache, no stored-command replay, no recipe-expansion cache on disk, and no state-dir env var — `--state-dir` defaults to the literal relative path `state`, so on a stateless CI checkout there is nothing to carry across runs, and even a surviving state dir cannot cause a skip because `record_failure` writes `status: failed` with an EMPTY hash and `determine_present_action` returns `Update` on any non-Converged status BEFORE it ever compares hashes. I reproduced the reporter's exact symptom locally with the 1.23.1 release binary in 0.1s per run: across five applies I rewrote the `command` twice (including adding a passing `exit 1` guard), and the console output was BYTE-IDENTICAL every single time — while a side-effect marker file proved all five distinct commands genuinely executed, and the on-disk run log contained the "missing" stdout verbatim. The leading hypothesis is confirmed: the operator-facing failure string is built from `out.stderr` only (`resource_ops.rs:411`, `machine_wave.rs:180`), so a task's stdout is invisible precisely when it matters. I additionally found that on the parallel/wave path no run log is written at all, so stdout is not merely off-console but destroyed. #391 fixes a real but different gap and is causally incapable of affecting the reported symptom, because the hash it feeds is only consulted for a lock entry whose status is already Converged.

### timing-summary
The reporter's "29.2s is too fast to be a real build" inference is invalid, and I refuted it three independent ways. (1) The 29.2s is per-machine wall clock and DOES include the task's own runtime (machine.rs:63 → machine_b.rs:68 → apply_summary.rs:131-138), but a default apply is SEQUENTIAL (policy.rs:112 parallel_resources=false; apply_gates.rs:163-169 makes --parallel the only override), so 29.2s is a SUM — and 4 of the 5 "failed" resources were dependents that forjar counted as failed WITHOUT executing anything (machine.rs:229-236, machine.rs:313-320, machine_b.rs:145-152 increment counters.failed and `continue`). Only one resource actually ran and failed. (2) I measured the reporter's actual workload on this machine's real llama.cpp CUDA tree: a WARM `cmake -S -B` reconfigure is 0.67s (cold 4.84s) and a full recursive make dependency walk over an already-built CUDA tree is 0.38s with ZERO nvcc invocations pending. The warm script costs ~1-5s, not 400-580s; the reporter compared a cold 159-.cu build against a warm no-op. (3) I reproduced the entire symptom on the shipped 1.23.1 binary with a 30-line local config: identical `JIDOKA: <machine>/<res> failed — dependents will be skipped: exit code 1: <stderr>` + the two `task=not-converged` lines, my stdout marker absent from the console, and — decisively — after EDITING the command's stdout text the console output was byte-for-byte identical across runs while `state/<m>/runs/<id>/<res>.update.log` showed the NEW text under `=== STDOUT ===`. Nothing on the apply console path reads a stored error; the JIDOKA string is built from this run's ExecOutput (resource_ops.rs:411, machine_wave.rs:180). Better still, I found that the reporter's own "CMAKE_BUILD_TYPE=Release" prefix is llama.cpp's `message("CMAKE_BUILD_TYPE=${CMAKE_BUILD_TYPE}")` at <HOME>/src/llama.cpp/CMakeLists.txt:15 — a bare `message()` is NOTICE mode, which CMake writes to STDERR, alongside 50 lines of `--` STATUS output that go to stdout and that forjar throws away. This is an observability defect, not a replay. I also found four adjacent defects, including that the parallel wave path skips completion_check verification entirely.

### live-repro
I built a minimal local-transport reproduction of #390 and it reproduces the reporter's symptom byte-for-byte on the first try, with the leading hypothesis fully confirmed and the reporter's "cached transcript / poisoned lock" theory positively refuted. A `type: task` whose command echoes a unique marker to STDOUT, a different marker to STDERR, and appends to a counter file, paired with an always-failing `completion_check`, produces exactly: `JIDOKA: ci-runner/llama-cpp-build failed — dependents will be skipped: exit code 1: FORJAR390_STDERR_MARKER cmake-warning-lookalike` followed by the two `task=not-converged:` lines. The stdout was never lost — it is written in full to `state/<machine>/runs/<run_id>/<resource>.<action>.log` and the parallel `.json`, and is recoverable via `forjar logs`, but nothing in the failure output points there, and on the reporter's stateless CI runner that directory is discarded with the workspace.
