# Quorum evidence — #405 (CRUX audit E03) — adjudicated claims

## CONFIRMED — 7 claims survived refutation

1. [probe] (explains-symptom) `sign --verify` deserialised the sidecar's `signature` and `signer` and then compared only a BLAKE3 content hash, so a forged signature printed `"valid": true` and exited 0.
   - evidence: Measured on the unfixed tree with `"signature": "deadbeef"` and `"signer": "root@prod"` in the sidecar: `{"valid": true, "signer": "root@prod", "algorithm": "blake3-hmac"}`, exit 0. The verifier was `verify_recipe` at src/cli/recipe_signing.rs:56, whose only check was `current_hash == sig.blake3_hash` at src/cli/recipe_signing.rs:75; the branch deletes the module outright. Pinned by `forged_recipe_signature_is_never_accepted` in tests/falsification_e03_signatures_are_read.rs, RED with `src/` reverted.

2. [probe] (explains-symptom) `sign --pq --verify` set `classical_valid`, `pq_valid` and `both_valid` from the same single hash comparison; there was no lattice and no key.
   - evidence: src/cli/pq_signing.rs:43 built `pq_input = "{blake3_hash}:slh-dsa:{signer}"` and src/cli/pq_signing.rs:52 labelled it `slh-dsa-blake3-placeholder`; `both_valid` at src/cli/pq_signing.rs:89 was set from the single `hash_valid`; `both_valid: true` printed over two forged signatures. The module is deleted rather than implemented — the ticket's option (b) — because a "post-quantum" label on a hash is a false claim, not a stub. The agy lane independently confirmed the path "was never real … merely a simulated wrapper". Pinned by `forged_dual_signature_is_never_accepted`.

3. [probe] (explains-symptom) `lock-verify-hmac` re-hashed each lock into `let _hash`, discarded it, incremented `verified`, and looked for the signature at a path `lock-sign` never writes.
   - evidence: `cmd_lock_verify_hmac` at src/cli/lock_audit.rs:174 read the signature from `<state>/<machine>.lock.yaml.sig` (src/cli/lock_audit.rs:181, not where `lock-sign` writes), computed `let _hash` at src/cli/lock_audit.rs:189 and incremented `verified` at src/cli/lock_audit.rs:191 regardless. On a state dir whose only signature was the literal bytes `not-a-signature` it printed `{"verified":1,"unsigned":0}` and exited 0. Withdrawn: `lock-verify-sig --key K` at src/cli/lock_security.rs already recomputes `blake3(lock ++ key)` and compares — that one is real. Pinned by `garbage_lock_hmac_is_never_reported_verified`.

4. [design] The surviving verifier is key-bound: an attacker who can rewrite `state.lock.yaml` AND `lock.sig` cannot pass `lock-verify-sig` without the key.
   - evidence: `verify_machine_sig` in src/cli/lock_security.rs computes `hash_string(content ++ key)` and compares it to the stored signature; BLAKE3 is not length-extendable, so the concatenation is not forgeable from a known signature. The agy lane attacked this claim and confirmed it. `lock_verify_sig_rejects_a_one_byte_mutation` is the regression guard — green before and after, labelled as such in the file, because it is #405's success criterion applied to the surface that survived.

5. [probe] (explains-symptom) `digest --verify` echoed the sidecar's own `algorithm` claim into a verdict beside `valid: true` while the check that ran was BLAKE3 and nothing else.
   - evidence: Measured on the first cut: `sed -i 's/"blake3"/"ed25519-dsse"/' r.digest.json` then `digest --verify --json` printed `"valid": true, "algorithm": "ed25519-dsse"`, exit 0 — an asymmetric check that never ran, reported as run. `verify_digest` in src/cli/recipe_digest.rs now requires the recorded algorithm to equal the one it computes and reports the one it ran. Pinned by `a_forged_algorithm_name_is_neither_believed_nor_echoed`, RED with that guard reverted.

6. [agy] (partially-explains) `lock-audit` carried a dead "recompute and compare" block that looked like tamper detection and was not.
   - evidence: `audit_lock_integrity` at src/cli/lock_audit.rs:77 recomputed `blake3("{rname}:{status:?}")` at src/cli/lock_audit.rs:90, compared it at src/cli/lock_audit.rs:91, and did nothing with the result — "flag it but don't fail". The recorded hash is `hash_desired_state` over the resolved declaration, which this command does not have, so the comparison could never match and never fired. The agy lane read it as "detects tampering and exits 0"; it was worse — it detected nothing. Taken: the block is deleted and the function documents `lock-audit` as a FORMAT audit; tamper evidence is the `.b3` sidecar and authentication is `lock-verify-sig`. No behaviour change, so no falsifier — recorded as hygiene of the #405 defect shape.

7. [agy] (partially-explains) The `withdrawn()` helper accepted ANY clap rejection, so a re-introduced verb with renamed flags would have passed the withdrawal tests.
   - evidence: `withdrawn` in tests/falsification_e03_signatures_are_read.rs matched the phrase `unexpected argument` without checking what was unexpected; `sign --verify` re-added with `--verify` renamed would print exactly that and pass. Taken: the helper now takes the withdrawn name and requires clap's message to quote it (`'sign'`, `'lock-verify-hmac'`), so only the absence of that exact verb satisfies it.

## REFUTED — 3 claims killed

1. [agy] refuted 1/1 — `digest --verify` and `lock-audit` "still pass on a hash the attacker controls", so the branch fails to achieve verification on every remaining path.
   - corrected: True of the mechanism and wrong as a charge. The verb that made the false claim was `RecipeSign` at src/cli/dispatch_platform.rs:20 with its `--signer` at src/cli/commands/platform_args.rs:128; `digest` is documented in its module header and its clap help as "tamper EVIDENCE, not a signature — there is no key"; it makes no verification claim to fail. That is the whole point of the rename: the verb that claimed a signature and checked a hash is gone, and the verb that checks a hash says so. Unkeyed integrity is what `sha256sum -c` and Debian's `Release` hashes are before the signature is checked; the signature is `lock-verify-sig`.

2. [design] refuted 1/1 — The right fix for #405 was to implement real signatures (option a) rather than withdraw the verbs (option b).
   - corrected: There was nothing to implement behind: no key material, no key distribution, no algorithm — `--pq` (src/cli/commands/platform_args.rs:132) was a label on a second BLAKE3, dispatched at src/cli/dispatch_platform.rs:114 to `cmd_dual_sign`. Implementing Ed25519 or SLH-DSA under a CLI that already claimed them would have shipped a real signature with no answer to "whose key, obtained how", which is the question TUF and cosign exist to answer. Subtraction leaves one honest keyed check and one honest unkeyed one; a signing design is a ticket, not a hunk.

3. [design] refuted 1/1 — `lock_verify_sig_rejects_a_one_byte_mutation` is a falsifier of this change.
   - corrected: It is not, and the file says so: it was GREEN before the change. It is #405's success criterion applied to the surface that survived, kept as a regression guard. The falsifiers are the five that went RED with `src/` reverted, each for its own reason, and the algorithm-echo case that goes RED with only its guard reverted.
