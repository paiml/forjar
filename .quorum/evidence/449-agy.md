## VERDICT
The proposed fix is structurally unsound and must be rejected. While it turns the falsifier green, it does so by creating a "poisoned" generation that fundamentally violates the system's state-config parity, breaking multi-step rollbacks and causing `gc_generations` to evict the exact snapshot `undo` relies on.

## REFUTED CLAIMS
- **"destroy must record the generation it replaces"**: Refuted (`src/cli/destroy.rs:253`) — because `maybe_record_generation` is called *after* `cleanup_state_files`, it actually records the empty state produced by the destroy, not the state it replaces.
- **"a generation is a record of what happened"**: Refuted (`src/cli/generation.rs:46`) — a generation pairs a config with state, but because `destroy` doesn't mutate the config on disk, this creates a poisoned generation pairing an empty state with a config that still declares all resources.
- **"falsifier proves the destroy→undo roundtrip is fixed"**: Refuted (`tests/falsification_destroy_undo_roundtrip.rs:184`) — the falsifier only passes because `undo` rolls back to generation 0 and re-converges off its config; generation 1 (created by destroy) is never replayed, masking its corrupted config-state pairing.
- **"dry-run filtered destroys"**: Refuted (`src/cli/destroy.rs:150`) — `cmd_destroy` does not even accept a `dry_run` flag, meaning the hardcoded `false` passed to `maybe_record_generation` simply masks a missing capability compared to `apply`.

## CONFIRMED CLAIMS
- **RECORDING_PAUSED logic**: Confirmed (`src/cli/apply_snapshot.rs:105`) — `maybe_record_generation` actively checks the `RECORDING_PAUSED` thread-local, ensuring that if `destroy` is executed as part of an `undo` rollback path, it will safely and correctly skip appending a new generation.
- **Falsifier is not a vacuous pass**: Confirmed (`tests/falsification_destroy_undo_roundtrip.rs:139`) — the `control_apply_apply_undo_restores_the_earlier_generation` test successfully proves that `undo` actively mutates the filesystem back to earlier bytes, preventing a false positive on a silent no-op.
- **Partial failure handling**: Confirmed (`src/cli/destroy.rs:244`) — `cleanup_succeeded_entries` correctly leaves failed resources in the lock file, allowing the subsequent generation recording to capture this partial state accurately.

## UNIQUE FINDINGS
- **GC Eviction of Undo Target**: If `policy.snapshot_generations: 1` is configured, `destroy` creates generation 1 and `gc_generations` immediately evicts generation 0; when the user subsequently runs `undo`, the command will fatally error because the target generation 0 no longer exists (`src/cli/apply_snapshot.rs:129`).
- **Poisoned Future Rollbacks**: Because `destroy` records generation 1 with the original config (declaring resources) but empty locks, a user performing `apply` -> `destroy` -> `apply` -> `undo` will rollback to generation 1; `undo` will then run `cmd_apply` on generation 1's config and actively *re-create* the resources instead of leaving them destroyed (`src/cli/undo.rs:341`).

## CRUX SURVEY
How do other deployment systems model the state a destroy replaces?
- **Terraform**: Models state as a purely forward-moving ledger containing sequential serial numbers. A `terraform destroy` updates the state file (removing resources and incrementing the serial) but does *not* snapshot the Terraform HCL config alongside it. There is no config-replay `undo`; rolling back requires a user to apply a previous config commit or manually restore an old state backup.
- **Nix**: Models generations as immutable closures (symlinks in the Nix store) that fully describe both the configuration (derivation) and the exact filesystem state. A `nix-env -e` (uninstall) creates a new generation that perfectly aligns the absence of the package in the environment with a profile that no longer references it, allowing flawless bidirectional rollbacks.
- **Puppet**: Operates completely statelessly on the master side regarding execution history. The `--noop` flag simulates a catalog run, but there is no native `undo` command. State is represented strictly by the current manifests in version control, and reversing a change requires reverting the code in Git and re-running the agent.

The proposed Forjar design attempts a Nix-style rollback (pairing config and state) but executes it like Terraform (mutating state without modifying the source config). This design falls well below the industry default because it creates a split-brain generation where the recorded config contradicts the recorded state, breaking the fundamental invariant needed for a reliable `undo`.
