# Quorum evidence — PMAT-208 — the claims as put to the lanes

forjar 1.26.0 shipped on 2026-09-08. Its release workflow created the GitHub release as a draft prerelease, uploaded thirteen assets, and then `dist-artifacts` died: `forjar dist` resolves checksums from the public releases/download URL, which GitHub does not serve for a draft. The installer was generated by hand from the tag with `--checksums-file` and uploaded, and the release was promoted by hand. This branch repairs the job, pins the repair, and writes the release and dogfood receipts.

## Claims

- C1 The repair uses the interface forjar's own error message names: `gh release download --pattern SHA256SUMS` (authenticated, and a draft's assets are visible over the API) before the dist step, and `--checksums-file` on it — pinned at tests/falsification_release_workflow_shape.rs:369.
- C2 The draft-until-the-end design is unchanged: the release is still created as a draft prerelease and un-drafted by the final job — pinned at tests/falsification_release_workflow_shape.rs:177 and tests/falsification_release_workflow_shape.rs:241.
- C3 Both receipts carry exactly one `verdict:` line and end with their literal END marker, and every sha, tag, gate result and asset count in them matches the repository and the published release.
- C4 The release receipt says plainly what was done by hand and why, rather than reading as though the workflow completed.
- C5 Nothing in the diff is outside the ticket: the workflow job, its rule, the roadmap row, and the two receipts.
