I have investigated the issue by tracing the execution and output capture paths in `forjar`. The reporter's hypothesis—that `forjar` is caching the transcript or replaying a poisoned lock entry—is **incorrect**. 

The command is indeed re-running on the target machine. The confusion stems from a critical observability defect in `forjar` combined with a flawed `completion_check` provided by the reporter.

Here is the root-cause analysis and the concrete fix proposal.

### 1. Root Cause Analysis & Refutation

**The Caching Illusion (Observability Defect)**
The reporter stated they added `echo`, `nvcc --version`, and `grep` to the command, but never saw their output, while CMake warnings appeared consistently. 
This is because **`forjar` silently drops `stdout` when a task fails**.

In `src/core/executor/resource_ops.rs`, `handle_resource_output` formats the failure message using *only* `stderr`:
```rust
// file://<REPO>/src/core/executor/resource_ops.rs#L411-L412
Ok(out) => {
    let error = format!("exit code {}: {}", out.exit_code, out.stderr.trim());
```
When the script runs, CMake writes its Deprecation Warnings to `stderr`, while `echo` and `nvcc --version` write to `stdout`. Because the task ultimately exits with code 1, `forjar` drops `stdout` and only surfaces `stderr`. The diagnostics ran perfectly fine; `forjar` just threw the evidence away.

**Why the task exits 1 (The execution flow)**
The reporter noted the run took 29.2s, which is exactly how long an incremental no-op CMake build takes. The main command succeeded and exited 0. We know this because of the error message present in the logs:
```
task=not-converged: command exited 0 but completion_check still fails
```
This specific string is generated by `batch_script` in `src/resources/task.rs`:
```rust
// file://<REPO>/src/resources/task.rs#L252-L257
script.push_str(
    "  echo 'task=not-converged: command exited 0 but completion_check still fails' >&2\n",
);
script.push_str("  echo 'task=not-converged: the declared state was not reached' >&2\n");
script.push_str("  exit 1\n");
```
If the user's explicit `exit 1` guard had actually aborted the main command, the script would have exited immediately due to the outer `set -euo pipefail` and **never reached the `completion_check`**. The fact that `task=not-converged` printed to `stderr` proves the main command exited 0, moving execution into the `completion_check` block, which subsequently failed, printed to `stderr`, and triggered the `exit 1`.

**Why the reporter's `completion_check` is genuinely wrong**
The reporter is using a `completion_check` that greps a build artifact (e.g., `grep GGML_CUDA build/llama-cpp`). 
While `batch_script` correctly changes the directory to `working_dir` before execution, `forjar`'s plan and host verification phases use `check_script` (`src/resources/task.rs`). `check_script` **does not** `cd` into the `working_dir` when evaluating a `completion_check`:
```rust
// file://<REPO>/src/resources/task.rs#L72-L74
if let Some(ref check) = resource.completion_check {
    return verdict::single(check, "task=completed", "task=pending");
}
```
If the check uses a relative path, it evaluates relative to the user's `$HOME` during `check_script`, meaning it silently fails to find the artifact. The reporter should be using `output_artifacts` (which correctly handles `working_dir` resolution) or must use absolute paths / explicit `cd` within their `completion_check` script.

### 2. Concrete Fix Proposal

**File to modify:** `src/core/executor/resource_ops.rs`
**Change:** Update `handle_resource_output` to include `stdout` alongside `stderr` when formatting the error. 

```rust
// src/core/executor/resource_ops.rs (approx line 411)
Ok(out) => {
    let mut err_msg = String::new();
    if !out.stderr.trim().is_empty() {
        err_msg.push_str(out.stderr.trim());
    }
    if !out.stdout.trim().is_empty() {
        if !err_msg.is_empty() {
            err_msg.push_str("\n--- stdout ---\n");
        }
        err_msg.push_str(out.stdout.trim());
    }
    let error = format!("exit code {}: {}", out.exit_code, err_msg);
    let should_stop = record_failure(...)
```

*(Optional Enhancement)*: In `src/resources/task.rs`, `check_script` could be updated to wrap `completion_check` inside a `cd $working_dir` block if `working_dir` is defined, mirroring the behavior of `output_artifacts`.

### 3. Testing the Fix

To prove the fix works and can fail correctly, add a test case in `src/transport/tests_*.rs` or the equivalent task executor test suite:
1. Define a dummy task resource that executes:
   ```yaml
   command: |
     echo "CRITICAL_DIAGNOSTIC_STDOUT"

   ```
2. Assert that the resulting `ResourceOutcome::Failed` error string contains **both** `"CRITICAL_DIAGNOSTIC_STDOUT"` and `"CRITICAL_DIAGNOSTIC_STDERR"`. Prior to this fix, the assertion for the stdout string would fail.

### 4. What to tell the reporter

* **Refute the caching hypothesis:** Assure them that `forjar` is not caching the script transcript and the command is successfully running on the target.
* **Explain the illusion:** The fast 29.2s run was a successful no-op incremental CMake build. Because it succeeded, the script advanced to the appended `completion_check`. The check failed and exited 1. Because `forjar` had an observability bug that dropped `stdout` on failure, their `echo` and `nvcc` diagnostics were discarded, while CMake's `stderr` warnings were preserved—creating the illusion of a cached replay.
* **Explain the script-side defect:** Their `completion_check` is failing. Advise them that `completion_check` does not automatically evaluate inside the `working_dir` during the pre-flight plan check. They should either explicitly `cd` into the build directory within the `completion_check`, use absolute paths, or preferably switch to using `output_artifacts`, which handles directory resolution natively.
