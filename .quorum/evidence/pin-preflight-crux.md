# Quorum evidence — PMAT-579 / PMAT-581 / PMAT-582 — CRUX

The question surveyed: **when an infrastructure tool is run by a binary whose version does not satisfy the version the configuration pins, does it refuse, warn, or proceed silently?** This is the question PMAT-579 registers for forjar, which today proceeds silently. Each system below was checked by running it or by reading its source at the default branch on 2026-09-16 — none is recalled from documentation or memory.

- **OpenTofu 1.8.5 — RUN locally.** A `main.tf` holding `terraform { required_version = ">= 99.0.0" }`. `tofu init -input=false` exited **1** and `tofu plan -input=false` exited **1**, both printing `Error: Unsupported OpenTofu Core version` and `This configuration does not support OpenTofu version 1.8.5`. It refuses before doing any work, on both verbs, with no flag required.
- **Terraform — SOURCE, hashicorp/terraform@main.** `internal/terraform/version_required.go:19` `CheckCoreVersionRequirements` delegates to the config; `internal/configs/module.go` `(*Module).CheckCoreVersionRequirements` evaluates `if !constraint.Required.Check(tfversion.SemVer)` and appends a diagnostic with `Severity: hcl.DiagError` and `Summary: "Unsupported Terraform Core version"`. An error, not a warning. **Stated plainly: OpenTofu is a fork of Terraform**, so these two are one design lineage observed twice, not two independent confirmations. The refusal text quoted above is OpenTofu's, observed; Terraform's is read.
- **Pulumi — SOURCE, pulumi/pulumi@master.** `sdk/go/common/workspace/project.go:378` defines `RequiredPulumiVersion`, and `pkg/cmd/pulumi/operations/up.go:615` enforces it: `if err := plugin.ValidatePulumiVersionRange(proj.RequiredPulumiVersion, version.Version); err != nil { return err }`. The operation returns the error and does not proceed. The same field is referenced from `destroy.go` and `refresh.go`. Pulumi shares no lineage with Terraform, so this is the independent refuse-by-default data point.
- **Ansible — SOURCE, ansible/ansible@devel. The counter-example.** `lib/ansible/plugins/loader.py:1691-1697`: on a collection whose `requires_ansible` the running version does not satisfy, behaviour is chosen by `COLLECTIONS_ON_ANSIBLE_VERSION_MISMATCH` — `warning` calls `display.warning(...)`, `error` raises `AnsibleCollectionUnsupportedVersionError`. `lib/ansible/config/base.yml:327` sets **`default: warning`**. And `loader.py:1708-1710`: if the `packaging` module is unavailable it warns and **returns True**, so a check that cannot be evaluated passes.

## What was not surveyed

This lane covered PMAT-579's question only. **PMAT-581** (a controller-side content key for remote resources) and **PMAT-582** (a verdict for a partial inspection) were **not** surveyed here, and three systems for one question must not be read as coverage of three tickets. Each is a separate question with its own prior art, to be surveyed when the row is implemented.

Verdict: **accept** refuse-by-default (OpenTofu observed, Terraform and Pulumi read — refusal on both plan and apply, before any work, with no opt-in) and **reject** Ansible's posture on two counts: a mismatch defaults to a warning a run can scroll past, and a check it cannot evaluate passes silently. forjar today sits below even Ansible's default — it neither refuses nor warns — which is what PMAT-579 registers. The one forjar-specific exception the survey does not settle: the upgrade itself runs under the *old* binary, so a scoped `-r stack-tool-forjar` must remain allowed. None of the four systems self-upgrades through its own apply, so none offers prior art for that exception.
